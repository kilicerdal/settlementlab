## Correction-aware position observer

A dedicated financial-position outbox publishes complete gross, reversed and net amounts in the same transaction as each shared-ledger execution or approved compensation. Failed publication rolls back the financial change. Direct and queued executions both publish; funding and workflow-only changes do not pretend to be new financial executions.

This stream is separate from the historical settlement-delivery outbox. A delivered settlement remains historically delivered after compensation. The position projection can subsequently observe net zero without rewriting that history.

```sh
settlementlab-position-worker --db YOUR_DATABASE --once
# Omit --once for continuous delivery.
```

Each event has a stable ID, source trade version and sequence. The inbox deduplicates delivery; an older event cannot regress the projection. Projection/inbox commit before publisher acknowledgment, so a crash in that gap is replayed safely. Leases fence abandoned workers, delivery is bounded to eight attempts, and invalid/exhausted events become `BLOCKED`. A continuous worker backs off on transient storage contention; a one-shot worker reports `STORAGE_BUSY` and exits 75. No HTTP endpoint starts or faults a worker.

`GET /api/trades/{id}/position` reports authoritative totals, the observed financial snapshot, pending events and `CURRENT`/`LAGGING`. Source version identifies the financial event, not every later workflow change. The investigation screen shows both sets of numbers and links position events to their source journal. A projection with current numbers but undelivered older events is still labeled `LAGGING` until delivery catches up.

Schema-7 posted obligations receive an explicitly labeled `PositionBaseline` during upgrade, followed by normal future events. This captures current financial totals; it does not fabricate historical event delivery. Migration is transactional and repeatable.

## Read-only snapshots and indexed statement history

SQLite uses WAL. Writes retain `BEGIN IMMEDIATE`; read-only snapshots open a read-only URI, set `query_only`, and use a deferred transaction. Investigations, snapshots, readiness, evidence reads, reconciliation reads and observer reads use the read interface. A regression holds an established read snapshot while another thread commits an execution, then verifies that the reader still sees its original version.

Statement membership is indexed by trade ID. Imports record membership from both external rows and the internal comparison snapshot, preserving missing-external cases. Resolution links its evidence statement explicitly, including empty corrected statements. Schema migration backfills existing memberships once.

Investigation retrieval uses a shared 5,000-row budget, a preliminary membership bound, and a 16 MiB statement-payload bound before JSON materialization. Timeline construction separately enforces 5,000 nodes and final JSON export enforces 16 MiB. Exceeding a bound returns an explicit error; it never silently exports incomplete history. These are safety bounds, not pagination. Global journal-integrity reads still contribute to investigation cost.

```sh
python -m scripts.investigation_benchmark --statements 1000 --reads 20
```

A local development sample with 0, 100 and 1,000 unrelated statement imports returned exactly one matching statement and used the membership index. Measured median/p95 read times were approximately 2.23/4.58 ms, 1.97/5.10 ms and 1.66/1.96 ms respectively. Warm caches and scheduling affect these small samples; faster later runs are not evidence that more history improves performance. CI produces fresh measurements with source provenance, not a production latency SLA.

## Explicit reconciliation bases

| Contract | Accounting basis | Meaning |
| --- | --- | --- |
| `/api/reconcile` | `GROSS_EXECUTED_RECEIPTS` | Legacy comparison with immutable gross execution receipts; compensation is not subtracted. |
| `/api/reconciliation/statements` | `NET_AFTER_APPROVED_COMPENSATIONS` | Full-statement investigation against execution less approved compensation, including zero-net rows. |

Responses identify the basis and relevant contract version/migration target. The lifecycle screen identifies net comparison; the legacy workbench labels its synthetic gross comparison. Neither endpoint silently changes the other contract.

Clients requiring post-correction reconciliation should adopt the newer statement-import/case workflow, supply full net statements, and preserve old statement snapshots and decisions. A legacy gross `BALANCED` result does not establish net reconciliation. No forced sunset date or automatic client migration is introduced.

## One command for integrity and scoped economic verification

```sh
settlementlab-incident --verify incident.zip --expectations accepted-plan.json
```

The verifier first checks bundle members, duplicate JSON fields, content checksums, trade identity and correlation integrity. It then independently checks accepted terms, exact original financial legs, full-batch compensating legs, checker separation and gross/reversed/net receipts against the **separate supplied plan**. Failure returns nonzero and identifies the control. It never derives the expected numerical terms from the bundle under review.

The expectation contract is version 1, bounded to 64 KiB:

```json
{
  "format_version": 1,
  "trade_id": "SL-000001",
  "terms": {
    "buyer_id": "SYN-ALPHA", "seller_id": "SYN-BROKER", "symbol": "NOVA",
    "quantity": 100, "price_cents": 4275
  },
  "executions": [{"batch_id": "ORIGINAL_BATCH_ID", "quantity": 40}],
  "compensations": ["ORIGINAL_BATCH_ID"]
}
```

Use separately retained accepted terms and execution plans. The demonstration writes its declared numeric expectations outside the ZIP; execution identities come from command receipts. A real reviewer must establish the independence and provenance of their own expectations. Untrusted self-supplied expectations cannot authenticate an equally untrusted bundle.

Without `--expectations`, legacy verification remains available but reports `CONTENT_INTEGRITY_ONLY` and `economic_verification: NOT_RUN`. A deliberately defective, rechecksummed compensation passes that layer and fails combined economic verification. The combined check is scoped to this obligation's executions, compensations and receipts; it does not independently verify global funding, market truth, identity authentication or author signatures.

## Expanded local AI evaluation

The corpus now includes 34 declared contract fixtures and six live-sample contexts: empty evidence, worker interruption, partial/discrepant execution, resolved/compensated execution, lagging position, and a complete incident. Each local context can be repeated 1–5 times, with at most 30 calls.

```sh
settlementlab-evaluate-investigator --live-model qwen2.5:3b --repeats 2 \
  --output artifacts/v44-ai-live
```

Reports distinguish structured grounding, citation validity, schema failures, correct abstention, unnecessary abstention and repeat consistency. The runtime permits conservative abstention; usefulness metrics measure when it happens despite supplied observations. Context/corpus hashes, prompt version, timings and raw responses are retained.

On November 22, 2026, an already installed free local model produced 12 recorded outputs across six contexts/two repeats. All passed declared grounding checks and expected abstention behavior; no unnecessary abstentions or invalid structured citations were observed, and claim/abstention signatures were consistent across each pair. [Retained actual sample](examples/incident-ai-v44-local-sample.json).

This remains a small synthetic development sample. Zero detected unsupported structured claims does not prove unrestricted prose is true, general accuracy, adversarial robustness or future consistency. Offline fixtures are not live model outputs. CI runs deterministic fixtures without downloading or invoking a model. No paid service is used.

## Upgrade and verification

Schema 7 → 8 is additive and transactional. The genuine V4.3 drill preserves existing financial rows and posted obligations, recovers pending work once, verifies refusal by the old release and restores its pre-upgrade backup:

```sh
python -m scripts.v42_compatibility --source-release v4.3.0 --output artifacts/v44-compatibility
python tests/browser/consistency_smoke.py
```

The online backup helper finalizes a standalone DELETE-mode image, closes source/destination handles before hashing or returning, and rejects pre-existing destination sidecars. A regression backs up newer committed work while another reader pins an older WAL snapshot, then verifies a copied standalone restore.

Back up and verify restoration before upgrading. WAL sidecars are part of a live database: use the supported SQLite online-backup tool, not a filesystem copy of an active database. Preserve post-backup work before restoring an earlier recovery point. [V4.4 recovery procedures](runbooks/POSITION_AND_VERIFICATION.md).
